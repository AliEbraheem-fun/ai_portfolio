T5 Span Corruption

T5's pretraining objective rebuilt by hand and checked against what the theory claims. The requested noise ratio holds only on long inputs: 0.15 comes out as 0.154 at 512 tokens but 0.212 at 32, because the loop stops only after the quota is exceeded, so the final span always overshoots. The geometric length distribution puts a third of spans at a single token and barely 2 percent past ten. The lesson's expected output also does not reproduce from a clean random.seed(42): the code is correct, but those exact spans require seven random draws to be consumed first. NER as Generation (RuMedNER)

Four approaches to one medical NER task, scored on a single metric with honest timing. Fine-tuned BERT wins on every axis at F1 0.426 and 7 ms per example, 131x faster than vLLM and 315x faster than naive generation, and it wins while being the wrong model for the job: bert-base-cased splits Russian into 4.58 subword tokens per word, effectively character level. Qwen3-1.7B under vLLM constrained decoding, given a Pydantic schema and zero training examples, reaches 0.250 and beats a fine-tuned mT5-small at 0.175. Per-class F1 turns out to track vocabulary shape rather than frequency: Drugclass scores 0.718 from 232 training entities while DI scores 0.302 from 995. Three silent failures are documented, none of which raises an exception. StrEnum requires Python 3.11 and the lesson VM ships 3.10, where the obvious backport makes str() return 'A.drugname', so every predicted tag is dropped and F1 becomes exactly 0.000. Constrained decoding guarantees the format but not termination, and 19 of 100 answers ran to the token cap emitting the whitespace a JSON grammar permits. And padding seq2seq targets with pad rather than -100 sends 96 percent of the training signal into predicting emptiness, which is what produces the looping output.

RAG from Scratch

A retrieval-augmented generation system built by hand on transformers and sklearn, no frameworks: rubert-tiny2 for embeddings, cosine similarity for search, Qwen2.5-1.5B-Instruct for answering, running end to end on CPU in 1.7 minutes. Under two percent of the system's parameters do the retrieving, and the whole twelve document knowledge base fits in 14.6 KB. Three bugs in the reference solution are reproduced and measured, none of which the lesson's own demo can reveal. A double argsort returns ranks instead of sorted order, which is provably harmless at exactly two documents because every permutation of two elements is its own inverse, and the demo uses exactly two; at three it is already wrong 33.7 percent of the time and at ten it returns the wrong best match 79.3 percent of the time. np.vstack is called with a PyTorch dim argument, so the second insert raises and leaves texts and vectors misaligned. And padding every short fact to 512 tokens costs 33.5x the compute for a byte-identical result. The retrieval failure is the dangerous one: it returns real documents, just the wrong ones, so the model answers fluently and the system merely looks underinformed.

Cross-Encoder Reranking

Four rankers measured on the same labelled candidates with NDCG, MRR and P@3, plus the cost that makes retrieve-then-rerank exist at all. The lesson's own output reproduces to six decimals, including the result it waves away as models making mistakes: asked how to choose a laptop for work, its cross-encoder ranks how to connect a laptop to a TV first. That is the checkpoint, not the architecture. stsb-roberta-base is trained on Semantic Textual Similarity, so it scores a question against its own correct answer at 0.3487 while scoring a paraphrase at 0.7611, and it gives a perfect COVID symptom match 0.2071 against 0.2064 for an unrelated Python versus JavaScript pair. Swapping to a relevance-trained ms-marco checkpoint fixes the ranking and is five times smaller and seven times faster. The uncomfortable finding is that on this corpus reranking earns nothing at all: a plain bi-encoder wins on one query and on four (NDCG 0.996) while costing 560x less per pair than Qwen3-Reranker, because ten short titles with one obvious answer each is too easy a task to need it. Cost is what justifies the architecture instead: reranking a million documents takes 191 hours with Qwen against 3.9 seconds for brute-force bi-encoder scan, since a bi-encoder encodes each document once at index time and a cross-encoder must redo every pair per query. Also documents how bfloat16 collapses 0.999457 to exactly 1.0.

arXiv Retrieval System

Graded module project: search 98,213 arXiv abstracts, hit MRR@5 above 0.91, and profile every component. Final score 0.9386, and the interesting part is that no single method gets there. TF-IDF reaches 0.8236, a dense MiniLM bi-encoder 0.8531, fusing both by Reciprocal Rank Fusion 0.8981, still short; only cross-encoder reranking clears the bar at 0.9293 over 20 candidates and 0.9386 over 50. Both models are 22M parameters, so the target is met by architecture rather than model size. Reranking barely improves Recall@5 (0.955 to 0.972) while moving Hit@1 from 0.858 to 0.913 — retrieval was already finding the right paper and simply not ranking it first, which is exactly what MRR punishes when there is one correct answer per query. Profiling produced a counterintuitive bottleneck: inside dense search the index costs 4.15 ms against 0.46 ms to encode the query, nine times more, and IndexFlatIP scales linearly from 0.22 ms at 5k documents to 4.22 ms at 98k, extrapolating to 430 ms at 10M. The cap on this system is the flat index, not the neural network — while the cross-encoder is 97 percent of per-query latency. Written to run fully offline after the VM turned out to have no route to HuggingFace at all.

Fuzzy Matching and Levenshtein

Classical string matching with no model at all: Levenshtein written out from the DP matrix, then rapidfuzz doing the same work at scale. The lesson's brand-search exercise fixes a threshold of 0.2 and observes that one threshold serves long and short names badly. Sweeping all 99 thresholds says something stronger: 6 wrong brand decisions is the floor for that scheme, and 0.2 is already the optimum. fuzz.ratio is 2M/(len(text)+len(brand)), so the score carries a hard ceiling set by what fraction of the text the name occupies, and for 60 of the 168 text-brand pairs a verbatim mention still cannot reach 0.2; Nike Inc. tops out at 0.209 against a 0.2 threshold. No threshold fixes this, because the threshold is the last step and the mistake is made earlier, in choosing what gets compared to what. Slicing texts into word n-grams, adding first-word aliases so Sony matches Sony Interactive Entertainment, and filtering by length gives 0 errors across 30 consecutive thresholds. Metric choice then sets how wide that band is: plain Levenshtein charges two edits for a swapped pair of adjacent letters, confirmed on 4811 random transpositions at 100 percent, so it scores Appel against Apple at 0.600 and drops it, while OSA scores 0.800 and triples the usable band. The fix costs 19x the time, 56.6 microseconds per text, and still no GPU. Also documents that the lesson's own formula returns similarity rather than distance: it agrees with normalized_similarity on all 3000 random pairs and with normalized_distance only on the 12 where the value is exactly 0.5, the single fixed point of x to 1-x, which is precisely the example the lesson chooses to illustrate it.

OpenSearch Full-Text Search

BM25 and boolean queries on a live OpenSearch 2.16 cluster, done on the course VM. Both exercises reproduce the author's solution exactly, including the hit order, and that order is the first thing worth explaining: a range clause inside should contributes a flat 1.0 while the BM25 match on author scores 0.9066489, so a placeholder row whose author is literally "unknown" outranks the actual Dostoevsky book. Second finding contradicts the lesson directly: should is only OR while it is alone in the bool. Adding a must or a filter drops minimum_should_match from 1 to 0, should stops selecting and becomes a score bonus, and the result set silently grows from 2 documents to 3 with a book that matches neither clause. Nothing errors. Third, the score is reproduced by hand to within 1.07e-08, which exposes all three ways Lucene departs from the textbook formula the lesson prints: the (k1+1) factor is hoisted into boost, lengths are per-field rather than per-document, and IDF carries a +1 inside the log. That last one is not cosmetic. Without it IDF turns negative once a term appears in more than half the corpus, so a document is penalised for containing the query word, and penalised harder the more often it appears (-1.37 for one occurrence, -2.15 for three). Fourth, exercise two's fuzziness does nothing: the English stemmer folds Moby and mobi to the same term, and the query returns an identical document at an identical 1.0926 with the fuzzy matcher removed. Fifth, term-level probes show Lucene scores transpositions as one edit, not two, so it is Damerau-Levenshtein rather than plain Levenshtein, and AUTO allows 1 edit at 3-5 characters and 2 beyond. Also flags that the lesson's own track data has title and artist swapped, and that the VM ships Python 3.12 with no pip against a page promising 3.10 with pip.

LSH Text Deduplication

MinHash and LSH built by hand, then reproduced in datasketch, to find near-duplicate documents without embeddings. The lesson's own worked example turns out not to reproduce: it builds the shared vocabulary from a Python set, and set iteration order depends on the interpreter's hash salt, so the same random.seed(42) lands on a different token order every run, verified across four hash seeds. More consequential, the lesson estimates signature similarity as the Jaccard of the signature's value-set rather than the fraction of matching positions, which is the standard MinHash estimator; measured against 600 pairs with known ground truth, that choice overestimates true Jaccard by 0.31 on average and by up to 0.81 in the worst case, while the positional estimator stays within 0.04. The banding formula p = 1-(1-s^r)^b itself checks out, confirmed to within 0.01 against both synthetic data and real MinHash signatures. The deduplication exercise's own expected answer turns out to be a coin flip rather than a fact: at the assignment's num_perm=18 it appears in only 49.8% of random seeds, and datasketch's own default seed produces an empty result instead of the lesson's answer, because the formula gives that exact pair a 67.7% chance of ever becoming a candidate, not a certainty. Finally, LSH's promised speedup over brute-force comparison is measured rather than asserted: 5.6x at 400 documents, 69.4x at 3,200, tracking the predicted quadratic-versus-linear growth almost exactly, with the false negatives and positives of an approximate method quantified alongside it.

Deduplication Showdown Bug

A course exercise comparing FAISS-plus-embeddings against LSH for near-duplicate detection on 5,000 labeled texts, run on a rented Tesla T4, turned into finding a real indexing bug in the published reference solution. Its dedup loop reads for i, emb in enumerate(self.embeddings[1:]), which numbers elements of the slice rather than the original array, so every recorded index from the second document onward is off by one; confirmed on a toy example where added_ids comes out [0, 0, 1, 2, 3, 4] instead of the correct [0, 1, 2, 3, 4, 5], then confirmed again on the real embeddings, where the shift flips the duplicate/unique label for 2,702 of the 5,000 texts. That single-line bug is the entire reason the lesson concludes LSH beats embeddings by a wide margin: the reference f1 of 0.6908 reproduces almost exactly (0.6910) when the bug is left in, but correcting the index alone raises f1 to 0.9526 with perfect precision, cutting the gap with LSH's 0.9661 from 0.28 to 0.0135. The lesson's own headline claim turns out to be an artifact of broken code, not a property of the two methods. A second, unrelated bug sits in the lesson's own answer for the metrics task: all three LSH lines pass df["pred_embed"] instead of df["pred_lsh"], which the notebook demonstrates by running that exact code and showing f1_lsh come out identical to f1_emb, contradicting the lesson's own printed expected output. The one claim that does hold up without qualification is speed: LSH cleared the dataset in 5.59 seconds against 747.1 seconds for embeddings, 133 times faster with no GPU. Also documents that transformers 5.x now loads Qwen3-Embedding-0.6B in bfloat16 by default, breaking a bare .numpy() call, and that the precode's batch_size=128 OOMs on a 15GB T4 since the reference ran on an A100.

LangGraph Agent Pitfalls

A course exercise building a calculator ReAct agent and a two-agent researcher-plus-chart-generator network on LangGraph, done without an OpenRouter or Tavily key on hand: rather than fabricate a single line of agent dialogue, the notebook verifies everything constructible offline and marks the rest as unexecuted. That still surfaced a real bug in the lesson's own precode. Passing model="deepseek/deepseek-chat-v3.1:free" as a bare string to create_react_agent does not reach OpenRouter at all: LangChain's model-string provider inference reads the "deepseek" prefix, routes through the langchain-deepseek package toward DeepSeek's native API, and demands its own DEEPSEEK_API_KEY instead of the OpenRouter credentials configured everywhere else in the lesson, reproduced as a live ValidationError even with a placeholder key. The same model identifier resolves to two different providers depending only on how it is passed, and the fix is the exact pattern the lesson's own second task already uses: construct ChatOpenAI with openai_api_base pointed at OpenRouter explicitly and pass the object instead of a string. A second finding is more structural: task two's Command[Literal["chart_generator", END]] return-type annotation on each graph node is not decorative, it is what lets draw_mermaid_png statically discover the dynamic routing at all. Stripped of the annotation, the rendered diagram shows both agent nodes as disconnected points despite identical runtime behavior; restored, it reproduces the lesson's own claimed result exactly, both directions between the two agents. Also documents that langgraph.prebuilt.create_react_agent is deprecated as of LangGraph 1.0 in favor of langchain.agents.create_agent, and that langchain-experimental, the only source of the PythonREPL tool the second task depends on, is officially being sunset.

MCP Weather Server

A course exercise on agent-tooling frameworks (autogen, smolagents) and MCP, done without an OpenRouter key: framework demos are built from the lesson's real code and verified up through client and agent construction, but no LLM call was faked. The graded task needed no key at all, an MCP server wrapping the keyless Open-Meteo API, and that let it be tested for real on three separate levels: calling the server's functions directly as plain Python, a full protocol round trip through a genuine MCP client over stdio, and converting the tool schema into OpenAI's function-calling format, all against live weather data. VQA Model Mismatch

A demo-only VQA lesson on image description, coordinate-based object detection, and where these models hallucinate, run for real on a local RTX 4070 Laptop (8GB VRAM) rather than documented from the page. Running the code as literally written surfaced a real gap between the lesson's prose and its precode: the text describes the capabilities of Qwen2.5-VL-7B-Instruct throughout, but the code block actually imports Qwen3_5ForConditionalGeneration and loads Qwen/Qwen3.5-0.8B, an unrelated, far smaller model from a newer hybrid-attention family. On the helmet-detection task the gap is measurable, not cosmetic: asked to tag each detected person with a wearing-helmet or not-wearing-helmet sub_label, the 0.8B model returned accurate bounding boxes for both cyclists but the sub_label field for neither. The same prompt against Qwen2.5-VL-3B-Instruct, the closest available match to the model actually named in the lesson, correctly tagged the helmeted cyclist while still missing the second, direct evidence that the printed expected output was generated by a different model than the one the precode hands the student. Also reproduces the lesson's own hallucination demo, a 3x3 grid of nine distinct wild cat photos, with a different but equally wrong answer each time: the lesson's model claimed 12 animals with a mix of real species, this run claimed 10 and misclassified all of them as a single species, confirming that this class of counting-and-discrimination failure recurs reliably even though its specifics never repeat between runs or models.

SigLIP2 Dataset Auditor

A dataset quality-control exercise: nine images labeled only by filename, validated against their filenames using google/siglip2-base-patch16-naflex, done for real on a local RTX 4070 rather than described from the page. The very first attempt to open the dataset failed outright: leg.jpg refused to load, and its magic bytes turned out to read an AVIF container header rather than JPEG, someone had renamed a .avif file to .jpg without re-encoding it, a real technical defect in the data sitting a full step before the labeling-quality question the exercise is actually about. Fixed with an AVIF decoder plugin, then continued for real: sigmoid similarity scores split into two dense clusters with a complete gap between 0.09 and 0.53 and not one image landing in between, and K-means on that single feature isolated a low-confidence cluster of exactly six files, burger, car, cats, lamp, leg, lizzard, matching what the lesson calls out by hand with no extra file and none missing. Opening the actual images explains three distinct failure modes inside that one cluster: leg.jpg is literally a photograph of a hand, a wrong label rather than a model shortfall; cats.jpeg frames two cats alongside a dog, a partially wrong label; and car.jpg and lamp.jpg show an ordinary sports car and an ordinary desk lamp that match their captions exactly, yet the model stayed unconfident anyway, a genuine model miss rather than a labeling error, exactly the puzzling case the lesson names without explaining.

CLIP Product Search

A text-to-image product search engine for a 44,441-item fashion catalog, built by fine-tuning openai/clip-vit-base-patch32 and running for real on a local RTX 4070 rather than described from the brief. The brief set a bar of mean CLIP score above 30, and the pretrained model measured 29.72 on the held-out 4,416 products, so the target could only be reached by genuinely training something. Four epochs of standard symmetric contrastive loss took it to 31.39 while loss fell monotonically from 0.53 to 0.17. The run contained a trap worth naming: epoch one reports a mean training CLIP score of 29.59, below the untrained model, which reads like fine-tuning actively damaging it. It is not. The training mean averages over the whole epoch including the first few hundred steps that knock the weights off their pretrained optimum, while validation measured at that same epoch's end already reads 29.80, above both the start and the epoch average, so the metric was climbing inside the epoch that appears to fail. Stopping there would have produced exactly the opposite conclusion to the correct one. Exploratory analysis surfaced the dataset's real constraint: these are marketing cards, not captions, with a median of 102 words, and 62.6% run past CLIP's 77-token text limit, so the model systematically reads only the opening of each description. The search half precomputes embeddings for all 44,158 catalog images once in 502 seconds into a 90 MB matrix, reducing each query to one text encode plus one matmul at 47 ms, roughly ten thousand times faster than recomputing image vectors per query. The sharpest result came from the "mickey mouse" query: its top hit is a shirt whose description mentions mickey only at character 445, past the truncation point, meaning the model never saw that word paired with that image during training and ranked it first on visual recognition alone.

SFT on an Instruction Set: What Four Methods Cost

One dataset, one model, one set of hyperparameters, varying only the training method, with peak VRAM and seconds-per-step measured for each. Full fine-tuning of a 0.6B model at length 1024 runs out of memory on an 8 GB card, so LoRA is not an economy here but the only way to train at all. int8 quantisation then does the opposite of its billing: 5.43 GB against LoRA's 4.61, and 2.2x slower per step, because on a small base the dequantisation overhead outweighs anything saved. Gradient checkpointing was the one knob that behaved as advertised, trading 17 percent of memory for 64 percent more time.

Inference Efficiency: Prompting, Speculation, Quantization

A marketplace case study generating 100 product descriptions under a fixed quality metric, measuring latency and throughput for each optimisation.
